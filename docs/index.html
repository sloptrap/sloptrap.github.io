1. Rule Definition Studio (sloptrap)

The core sloptrap/sloptrap repository provides the Svelte 5 + Tauri v2 Rule Definition Studio, which runs either directly in the browser (launch hosted Studio) or as a native desktop app:

  • Known Slop & Known-Good Channel Sets (AiSList & Extension): Load specified lists of Known Slop and Known Good channels/accounts (import channels flagged directly in sloptrap-extension, load YouTube slop channels from Override92/AiSList, or paste @handles/URLs) to measure live rule effectiveness (Recall, Known Good Safe %, False Positives, and F1) against their content.
  • Publish → private review pipeline → Community tier: Publish to Leaderboard sends the rule project to the Cloudflare Worker (POST /api/v1/rules/publish, Turnstile-protected, exact-origin check), which validates it, rejects duplicates and stores it as pending. A private pipeline then compiles it with the trusted compiler, runs the static WASM audit and a hidden-holdout behavioural audit with a false-positive ceiling, and only then signs it with the community key as community-<slug>. Community rules are not reviewed or endorsed by maintainers and are never shown as verified; clients keep them disabled until the user turns on "Community rules". Nothing is compiled or signed in this public repository.
  • Common Cross-Site Rule Syntax: Switch freely between the clean sentence-style Visual Builder and a readable cross-site DSL sharing signals such as post.frequency, account.dormancy_days, post.title_reuse, text.formal_prose, voice.pacing_variance, and media.synthetic_ratio.
  • Shared Variables & Threshold Actions: Rules can add or set values on shared variables (e.g. suspicion, script_risk, voice_risk) accumulated across multiple rules and checked against thresholds (block, hide, dim, warn).
  • Token Sliders & .strule Export: Tune $token sliders with live microsecond WebAssembly recompilation, run the static WASM audit locally, and export sloptrap-bundle-v2 .strule files signed with your own key. A self-signed bundle is tier unverified: it can be loaded only by explicit local import, never from the registry.
# Example Common Cross-Site Syntax
token high_post_rate = 0.9
token block_cutoff   = 60
var suspicion = 0

rule "High daily post frequency"
  when post.frequency >= $high_post_rate ramp 1.5
  then add 36 to suspicion

decide "Block high-suspicion accounts"
  when suspicion >= $block_cutoff
  then block
git clone git@github.com:sloptrap/sloptrap.git
cd sloptrap
npm install

# Run in a browser
npm run dev

# Or run as a desktop application (Tauri v2 + Rust live URL extractor)
npm run tauri dev

2. Library & Drop-in UI Integration

Applications can embed SlopTrap either as a headless static rule evaluator or with prebuilt UI sections for full rule management.

Mode A — Static rule set (headless, zero network)

// JavaScript / Browser / Extension — sdk/sloptrap-sdk.js
import { SlopTrapStaticEngine, normalizeAccountSnapshot } from "https://sloptrap.github.io/sdk/sloptrap-sdk.js";

const engine = new SlopTrapStaticEngine({ site: "pinterest", verifiedOnly: true });
await engine.loadBundles([myStaticStruleJson]);

const fp = normalizeAccountSnapshot("pinterest", { handle: "@decor-mill-z4k", recentUploadsPerDay: 12 });
const verdict = await engine.evaluate(fp); // { score, action: "allow" | "warn" | "block" }
// Go — pkg/sloptrap (in sloptrap/sloptrap-tube-tui)
eng, err := sloptrap.NewStaticEngine(sloptrap.StaticConfig{
    Site:            sloptrap.SitePinterest,
    BuiltinVerified: true, // or BundlesFS: embeddedRulesFS / BundlesDir: "./rules"
    VerifiedOnly:    true,
})
verdict, err := eng.Evaluate(ctx, fingerprint)

Mode B — Drop-in UI sections for full functionality

<!-- Web / Browser Extension / Electron: Gravity UI Web Component -->
<script type="module" src="https://sloptrap.github.io/sdk/sloptrap-ui.js"></script>
<sloptrap-rules-panel site="youtube" verified-only></sloptrap-rules-panel>

Mode C — Pre-matched public rule lists (lists/<site>/<rule_id>.txt)

Every official rule has a matched-account list indexed by lists/manifest.json (with SHA-256 digests for delta sync). An account is listed only after reports from at least five distinct networks, and every row is re-validated when the site syncs (known site, official rule id for that site, well-formed account key). Clients check enabled official lists before running WASM; community rules never get lists and never use this fast path. Users can opt in (contributeMatchedAccounts: true) to report newly matched accounts.

3. Pluggable Target Site Adapters

Site adapters decouple platform DOM/API extraction from .strule WebAssembly execution. Built-in adapters cover youtube, tiktok, and pinterest, while custom platforms register in one call: 

import { registerSiteAdapter, normalizeAccountSnapshot } from "https://sloptrap.github.io/sdk/sloptrap-sdk.js";

registerSiteAdapter({
  siteId: "bluesky",
  displayName: "Bluesky",
  matchUrl: url => /bsky\.app/i.test(url),
  extract: actorData => normalizeAccountSnapshot("bluesky", actorData),
});

4. Example Applications

  • sloptrap/sloptrap-tube-tui (Example YouTube Forensic TUI & Server): Reference Go terminal application combining YouTube upload-history dormancy analysis, json3 caption prosody, optional 45-second ffmpeg EBU R128 dead-air probing, autonomous crawling, and local HTTP verification APIs with SlopTrap's .strule WebAssembly runtime.
  • sloptrap/sloptrap-extension (Chromium & Firefox Extension): Single-monorepo Manifest V3 extension filtering YouTube, TikTok, and Pinterest feeds in real time using static and registry-synced Official .strule bundles (plus Community bundles when the user enables them).

5. Bundle format v2, trust tiers & community rules

All clients (Studio, the JS SDK and extension, the Go runtime and this site's auditor) read only sloptrap-bundle-v2. v1 support has been removed and the old v1 signing keys (eb85cbf5…, 33fee5d9…) are revoked; a v1 bundle no longer loads anywhere.

  • Official: signed offline by a SlopTrap maintainer with the pinned official key 0540a396ece8ab0f9670a25e03b02e345450a1373b86a7d400dcad79ceec5cc1. The official key is not in any CI system. Official is the only tier shown as verified, and enabled by default.
  • Community: anonymous submissions that passed the private pipeline's automated checks, signed with the community key 34c3c2ee0d51ae18fbf669dc441a51faa06bbfcbf5efa6adf73702d644c5c69e. Their ids start with community-. They are not reviewed by maintainers, are off by default, and verified-only mode never loads them.
  • Unverified: any other key. Never loaded from the registry; only by explicit local import, and always labelled unverified.

The tier is computed from the signing key alone. Fields inside a bundle or a leaderboard feed (such as verified or provenance) carry no trust. Bundles are not encrypted: the v1 "encryption" used a key derived from a public seed, so it was only obfuscation, and v2 ships the plain WASM module. See the WASM spec for the signed fields and the audit rules.
